# 计算图编译与执行

GE 接收进程内 SDK 调用，管理计算图的编译、装载与执行，并通过 ACL/RT 将工作交给设备。

## 整图执行的准备

<Section id="graph-basics">

单个 kernel 通过设备地址完成计算。一个网络有大量相互依赖的算子；还需要决定每个算子的输入输出地址、中间张量何时可复用、任务在哪条 stream 上提交，以及跨流何时等待。GE 将这些整图工作组织为可复用的编译与执行过程。

### 图表达计算，执行需要资源与任务

以 $\logical{u}=\operatorname{MatMul}(X,W)$、$\logical{Y}=\operatorname{ReLU}(u)$ 为例，图中的数据依赖要求 ReLU 读取 MatMul 已产生的 $u$。执行还需要 $u$ 的实际内存，以及与 shape、dtype 对应的算子实现。跨 stream 时，这个生产消费关系还要落实成同步。

[ModelBuilder::BuildModelForGetTask](?fp=code&block=model_builder-1345-1393)把逻辑流分配、内存规划、算子编译和同步节点插入串在一起。整图视角使编译器能分析中间张量的生存期，并为不再同时使用的数据规划内存复用。

### 编译、装载与执行分别承担的工作

编译阶段准备图的执行方案；装载阶段为这份方案建立实际执行资源；后续执行使用本次输入触发计算。对固定模型反复推理时，权重、算子实现和执行资源可以跨次保留，新输入仍要进入本次执行。

静态执行器在加载时调用 [DoTaskSink](?fp=code&block=davinci_model-1279-1292)，执行时通过 [aclmdlRIExecuteAsync](?fp=code&block=davinci_model-7960-7966-8016-8036)触发已加载模型。把一组任务提前准备并组织起来，可以减少每次由 Host 逐个准备和提交的工作。模型中的多个算子仍可对应多个设备任务；整图触发与算子融合是分别发生的优化。

### Session 的组织作用

调用者通过 Session 注册、编译、装载和执行图，使用 graph ID 定位其中一张图。[ExecuteGraphWithStreamAsync](?fp=code&block=ge_api-632-661)再进入内部执行对象。Session 是图与执行资源的管理边界，同一张 NPU 上可以有多个 Session、多个图和多条 stream；实际资源共享关系由这些对象怎样创建和使用决定。

</Section>

## 静态与动态 shape 的执行成本

<Section id="shape-cost">

shape 决定中间张量需要多少内存，也影响算子的分块和执行参数。以 $\logical{Y}=\logical{X}W$ 为例，$X$ 的 batch 变化会改变输出和部分工作空间的大小。已知固定 shape 时，更多准备工作可以提前完成；运行前才知道的维度，需要执行时补齐相关工作。

### 静态 shape 提前固定的内容

固定 shape 使编译阶段可以确定更多张量大小、内存偏移和算子参数，再在加载时准备任务与资源。[静态模型执行入口](?fp=code&block=davinci_model-7960-7966-8016-8036)体现了这种复用：同一已加载模型接受新一批输入并再次执行。

输入地址仍可能每次变化，资源也需要正确管理；静态 shape 减少的是需要重新判断和准备的工作，并未消除 Host 的所有参与。

### 动态 shape 将必要工作留到执行时

动态 shape 的图拓扑可以保持不变，变化的是某些张量的实际维度。GE 的 [Lowering](?fp=code&block=graph_converter-854-874)将计算图转换成 ExecuteGraph，并分出初始化、主执行和清理部分；主执行中可以包含 shape 推导、内存处理和设备任务提交。

[SequentialExecute](?fp=code&block=sequential_executor-18-30)展示一种 Host 执行循环：按执行节点调用函数。某个节点在 Host 算出大小，后面的节点才能申请内存或提交使用这个大小的任务。动态执行路径因此可能出现设备等待 Host 准备的间隔；具体成本取决于编译后的执行图和实际输入。

### 分档、合批与多流解决的成本不同

如果输入 shape 只来自少数几个已知档位，可以为这些档位准备相应执行方案，代价是编译、装载和常驻资源增加。合批则改变一次执行的工作量；多流提供不同工作之间的重叠机会。它们分别作用于准备成本、单次计算效率和并发机会，收益需要在同一工作负载下比较。

网络结构固定与 shape 固定是两个属性。这里讨论的动态 shape 仍可以使用编译过的固定拓扑，而其中已知 shape 的子图也可能交给[静态执行器](#execute)。

</Section>

<TextNote desc="该入口拒绝 DFlow Session。">`Session::ExecuteGraphWithStreamAsync`</TextNote> 从进程静态 `g_session_manager` 查找 InnerSession 并直接调用。这条链是进程内调用，不是 GE RPC；边界之外的编译插件、AICPU 和驱动另有执行机制。

### 异步执行与设备完成条件

<CodeBlock language="cpp" code={`
ModelManager::ExecuteModelWithStreamAsync(...)
  ├─ HybridModel 存在 → HybridDavinciModel::ExecuteWithStreamAsync(...)
  │                    → RT2 wrapper → executor_->Execute(...stream/allocator...)
  └─ 普通静态模型    → ExecuteModelWithStream(..., true, ...)
                       → DavinciModel::NnExecute(async=true)
                       → aclmdlRIExecuteAsync(...caller_stream...)
`.trim()} notes={{"aclmdlRIExecuteAsync":"静态异步分支采用调用者 stream，is_inner_model_stream_=false；内建 stream 的显式同步分支以该标志为条件。","HybridDavinciModel::ExecuteWithStreamAsync":"Hybrid / RT2 使用独立执行路径，内部同步策略不能从普通静态分支推出。"}} />

$$
\begin{aligned}
\host{\mathrm{Success}(\mathrm{ExecuteAsync})}&\not\Rightarrow\device{\mathrm{Completed}(\annotate{stream}{s})}\\
\host{t_{\mathrm{host\_return}}}&<\device{t_{\mathrm{device\_complete}}}\quad\text{is possible}\\
\host{\mathrm{SyncSuccess}(s)}&\Rightarrow\device{\mathrm{Completed}(\mathrm{prior\ work\ on}\ s)}\\
\mathrm{safe\_reuse}(\annotate{buffer}{b})&\Rightarrow\device{\mathrm{Completed}(\mathrm{last\ device\ access\ to}\ b)}
\end{aligned}
$$

GraphManager 持每图 run\_mutex，设置 RunFlag，主机函数返回时 guard 清标记并释放锁。设备工作此时仍可能继续。因此 RunFlag=false 不足以证明 buffer 可释放；这把锁也不覆盖完整设备执行期。

```cpp
GraphManager::ExecuteGraphWithStreamAsync(...)
  → lock(graph_node->GetRunMutex())
  → SetRunFlag(true)
  → executor_->ExecuteGraphWithStream(...)
  → return / guard: SetRunFlag(false), unlock

Triton GE backend
  → ExecuteGraphWithStreamAsync(...)
  → aclrtSynchronizeStream(instance->stream)
  → D2H → 构造响应 → 释放本次 buffer
  → 本后端 Scheduler::Instance 恢复 IDLE
```

[Triton 后端](index.html#algorithm)通过自己的 `Scheduler` 保持所选 `Scheduler::Instance` 为 RUNNING，直到 stream 同步、回传和响应构建完成后才恢复 IDLE；这项生命周期约束不能由 GE 的 host-side RunFlag 替代。
