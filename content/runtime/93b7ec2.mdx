# NPU 数据与运行时执行

Runtime 承接 Host 程序对 NPU 的资源管理与任务提交：选定设备，准备存储，提交计算，建立依赖并等待完成。应用和 GE 使用的 ACL 接口在本仓转入 RT 实现。

<Annotations notes={{covered:"只覆盖对应 stream 的既有工作及其明确建立的工作关系，不代表其他并发使用者已完成。"}} />

<Section id="npu-basics">

## 设备、Context 与执行资源

CPU 执行 Host 程序；NPU 有自己的设备内存和计算核。**Context 是与一张设备关联的运行环境**，Host 线程通过当前 Context 使用该设备；**stream 是设备任务的执行序列**，在某个 Context 中创建。[对象关系与切换接口](?fp=code&block=runtime-context)对应下面的模型：

```text
Host 线程 → 当前 Context → 一张 NPU
                            ├─ 全局内存：输入、输出、权重
                            ├─ stream A：按提交顺序执行任务
                            └─ stream B：另一条任务执行序列
```

[最小样例](?fp=code&block=vector-add)在 `aclInit` 后用 `aclrtSetDevice(0)` 选定设备并使用默认 Context，再创建 stream。也可显式创建 Context 并设置为当前 Context；同一设备可有多个 Context，多个 Host 线程也可以共享一个 Context；每个线程维护自己的当前选择。切换 Context 影响后续操作，已创建的 stream 和已分配内存仍属于原设备。

</Section>

<Section id="memory">

## 内存与数据搬运

Host 存储和设备存储有各自的地址与生命周期。`aclrtMalloc` 申请设备内存，`aclrtFree` 释放；Host 可用普通内存，也可通过 [aclrtMallocHost / aclrtFreeHost](?fp=code&block=runtime-host-memory)管理锁页内存。输入输出传给 kernel 的是设备地址；标量参数直接传值。

```text
Host 输入 ── H2D ──> 设备输入 ── 计算 ──> 设备输出 ── D2H ──> Host 结果
```

[拷贝与填充接口](?fp=code&block=runtime-memory-copy)覆盖 H2D、D2H、D2D 及内存初始化。要让拷贝随 stream 异步推进，使用 `aclrtMemcpyAsync`；本版本在 Host 一侧使用锁页内存时异步提交，普通非锁页内存则等拷贝完成才返回。参与异步任务的源、目标存储都须保留到任务完成。

多卡下，每块缓冲区仍归分配它的设备；切换设备不会迁移数据。[跨卡直接拷贝](?fp=code&block=runtime-peer-copy)先检查并启用 Peer Access，再在支持的设备间执行 D2D。普通设备内存分配从[当前 Context 取得目标设备](?fp=code&block=api_impl-2391-2419)，不会每次另挑一张卡。

</Section>

<Section id="kernel">

## kernel、block 与 tile

**kernel 是 Host 启动的一段设备程序**。`__global__` 标记它的入口，`__vector__` 指定入口在 Vector 核执行；`__aicore__` 标记设备端函数，供入口或其他设备函数调用。因此 Vector 入口调用的 `__aicore__` 构造函数、`Init`、`Process` 也在入口所在的 Vector 核上执行。[官方函数限定符](https://asc.gitcode.com/guide/programming_guide/language_extension/simd_builtin_keywords.html)

[VectorAddDo](?fp=code&block=vector_add_kernel-30-34)通过 `<<<blockDim, ..., stream>>>` 启动 [VectorAddKernel](?fp=code&block=vector_add_kernel-16-21)。也可[显式加载算子二进制、取得函数句柄并启动](?fp=code&block=runtime-kernel-loading)；两种方式都要提供参数和执行 stream。

**block 是一次 kernel 启动中的一份逻辑执行**。各 block 执行相同程序、接收相同参数，通过自身编号分工，再由运行时调度到设备计算核；实际同时运行多少受可用计算核限制。小样例设置 `blockDim=1`，一个 block 完成 8 个 FP32 的 $\device{C}=\device{A}+\alpha\device{B}$，其中 $\alpha=1$。

[分块 Add](?fp=code&block=kernel_add-103-115)在每个 block 的入口内创建自己的 `KernelAdd`，由 [Init](?fp=code&block=add-block-partition)读取 block 编号并计算区间。例如 4096 个元素启动 4 个 block，程序将 A/B/C 划分为：

```text
block 0 → [   0, 1024)       block 1 → [1024, 2048)
block 2 → [2048, 3072)       block 3 → [3072, 4096)
```

**tile 是一个 block 内每轮搬运和计算的数据片段**。片上存储容量有限，[Process](?fp=code&block=add-tile-loop)把每个 block 的 1024 个元素再分为 16 个 tile，每轮处理 64 个。`GlobalTensor` 引用该 block 的设备全局内存区间，`LocalTensor` 引用本轮使用的片上缓冲区：

```text
GlobalTensor A/B → DataCopy → LocalTensor A/B → Add → LocalTensor C → DataCopy → GlobalTensor C
```

block 提供多核分工，tile 组织核内分批处理；区间由 kernel 代码计算。这里的 `DataCopy` 发生在设备内部，H2D/D2H 则跨越 Host 与设备内存。[官方张量与存储模型](https://asc.gitcode.com/guide/programming_guide/programming_model/ai_core_simd_programming/cpp_tensor_programming/cpp_tensor_programming_overview.html)

</Section>

<Section id="stream-basics">

## stream、Event 与完成条件

同一 stream 中的任务按序执行，例如输入拷贝之后才执行使用该输入的 kernel。多条 stream 提供独立工作的重叠机会，**跨 stream 的数据依赖由程序建立**。[加 1 再乘 2 的样例](?fp=code&block=main-35-69)让两条 stream 访问同一个初值为 0 的数值；要得到 2，后者必须等前者完成：

```text
stream A：加 1 → RecordEvent(ready)
                         │
stream B：WaitEvent(ready) → 乘 2
```

Event 标记 producer 执行到某个位置，consumer 在 stream 内等待该标记；Host 可继续提交后续工作。[Event 接口](?fp=code&block=runtime-events)还提供状态查询、Host 等待和时间测量；[跨流拷贝样例](?fp=code&block=main-146-160)把同一依赖用于 H2D 与 D2H。

</Section>

<Section id="stream">

异步接口成功返回，只说明提交成功。Host 要使用结果或复用存储，需建立完成条件：用 aclrtSynchronizeEvent 等某个 Event、aclrtSynchronizeStream 等某条 stream，或 aclrtSynchronizeDevice 等当前设备的工作完成。[stream 创建与同步的调用关系](?fp=code&block=stream-handles)最终转入 RT；同步覆盖该执行序列的既有工作及其依赖。

$$
\host{\mathrm{Success}(\mathrm{SubmitAsync}(s))}\not\Rightarrow\device{\mathrm{Completed}(s)},\qquad
\host{\mathrm{SyncSuccess}(s)}\Rightarrow\device{\mathrm{Completed}(\annotate{covered}{\mathrm{covered\ prior\ work}})}
$$

[异常信息接口](?fp=code&block=runtime-errors)用于取得错误和定位设备任务。设备执行错误可能到同步时才暴露，提交与等待两处都需检查返回状态；等待接口也提供超时形式。

</Section>

<Section id="model-execute">

## 模型执行与资源复用

重复的一组任务可以组织为 **模型运行实例**：通过[捕获 stream 任务或显式构建](?fp=code&block=runtime-model-reuse)准备一次；捕获阶段记录任务，之后再由 `aclmdlRIExecuteAsync` 反复提交，结束使用后销毁。这里保存的是可执行任务及其关系，神经网络的图解析和编译由 [GE](ge.html#graph-basics)等上层完成。

GE 的普通静态模型沿[模型异步执行调用链](?fp=code&block=model-api-call-path)进入 `rtModelExecute`；Hybrid / RT2 使用[另一执行分支](ge.html#execute)。这些是进程内接口调用，设备工作仍受 stream 的顺序和完成条件约束。

</Section>

<Section id="lifetime">

## 释放、并发与性能成本

设备最后一次访问完成后，输入输出缓冲区才能复用或释放。[小样例的清理路径](?fp=code&block=vector-add-cleanup)在同步、D2H 和结果检查后释放设备存储，再销毁 stream、重置设备并结束 Runtime。显式创建的 Context 由创建方销毁；默认 Context 随设备资源清理。已有合适缓冲区可反复使用，也可从一次较大的分配中划分输入输出区域。

Context、stream、加载的算子和模型实例可以跨次保留。串行重复同一工作、每次耗时相同的简化情形满足：

$$
T_N=\host{T_{\mathrm{setup}}}+N T_{\mathrm{run}},\qquad
\frac{T_N}{N}=\frac{\host{T_{\mathrm{setup}}}}{N}+T_{\mathrm{run}}
$$

复用摊薄准备成本；多 stream 尝试重叠独立工作。实际收益取决于 Host 提交速度、搬运与计算资源，增加 stream 不会增加硬件容量。[Triton 后端的 Scheduler](index.html#algorithm)也遵循同一生命周期：直到 stream 同步、D2H、响应构建和局部缓冲区清理结束，才归还共享执行资源。
